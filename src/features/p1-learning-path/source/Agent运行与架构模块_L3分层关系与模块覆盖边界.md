# Agent运行与架构模块｜L3分层关系与模块覆盖边界

**2026-10-16｜原正文的结构补充｜待验收**

原《现有内容整合与验收稿》的正文、12个主题编号、课程出处与证据限制全部保留。本补充把它们组织为可沿功能深入的内容关系，不重新写一套教材。

**先看功能，再看过程；需要解释某一步时，才进入支撑机制和具体技术。**

这里的四个深度全部属于 **L3内部**，不替代系统整体的 L1–L4。L1仍只有指定三项，L2仍暂按查询／生成分类，L4仍用于面试。

## 一、L3的整体关系

| 深入到哪里 | 回答什么 | 例如 |
|---|---|---|
| 功能 | 要完成哪类业务 | 查询资料、客户分析、合同、月报 |
| 执行过程 | 这类业务怎样做下来 | 取资料、处理结果、继续或交付 |
| 支撑机制 | 某一步为什么能运行、受什么限制 | Context、Skill、工具执行、Loop、状态、审批 |
| 具体技术 | 云帆用什么实现这些机制 | DeepAgents、LangGraph、CRM Service、SQLite、Word工具等 |

**功能包含处理过程；过程使用机制；代码和框架实现机制。** 这不是四级技术父子树。例如“客户分析使用 Tool”，不等于“Tool 是客户分析的一种”。

原主题1“整体分工”和主题2“Harness及框架”作为共用的架构说明：从具体过程需要时进入，不再要求先读完一排术语。

### 四条功能入口

- **查询资料：**取得有权限的客户或业务数据。
- **客户分析：**结合事实，按分析规则形成判断和建议。
- **合同生成：**根据订单资料与模板生成文件。
- **销售月报：**取得统计数据，按规则组织报告。

这四项是本稿已有内容的业务入口。它们沿用 L2 临时分类：查询资料归“查询”，其余三项归“生成”；不声称这是老师确认的统一分类。

客户分析、合同、月报都会复用查询过程。**查询只维护一份解释，三个业务引用它；不会各生成一套查询知识。**

## 二、功能怎样进入执行过程

以下路线是既有代码能力和课程规则的教学走查，**不是某次任务实际发生的完整Trace**。澄清、审批、补查按条件出现，不是每个任务必经。

### 功能一：查询资料

**过程：确定查询对象 → 提出查询 → 校验并执行 → 返回资料 → 继续或结束。**

| 过程中的问题 | 进入哪个支撑机制 | 云帆具体技术与原正文 |
|---|---|---|
| 当前要查谁、查什么 | 模型根据当前输入理解目标；不明确时应澄清 | 模型调用与Context来源；主题1、6。具体澄清行为未实测 |
| 怎样提出查询 | Tool名称、参数、可用工具范围 | CRM Tool注册与可见性过滤；主题3 |
| 谁真正读取数据 | 工具执行、权限和业务规则 | Python工具 → Next工具接口 → CRM Service → Repository/SQLite；主题3、11 |
| 返回的数据怎样用于后续回答 | 工具结果进入消息；后续模型调用获得相关信息 | ToolMessage及模型输入路径；主题5、6、7 |
| 查完是否还要继续 | Loop：继续查询或结束 | DeepAgents/LangGraph执行路径；主题5。某次补查原因待日志核验 |

**从过程进入正文：**先读主题3的查询链；遇到“结果怎么被看见”再读主题6；遇到“为什么继续查”再读主题5。权限和状态按相关步骤进入。

用户曾看到的“读取文件、再次查询沟通记录”等六步UI观察仍保留在主题5。它是一个观察样本，不是这项功能的固定标准流程。

### 功能二：客户分析

**过程：明确分析对象 → 查询相关事实 → 按规则分析 → 展示建议与依据。**

| 过程中的问题 | 进入哪个支撑机制 | 云帆具体技术与原正文 |
|---|---|---|
| 分析应回答哪些问题 | 任务说明与输出约束 | `crm-lead-analysis`；主题4、9。课程五项模板保留 |
| 事实从哪里来 | 复用“查询资料”全过程 | 线索、沟通、订单、商品查询；主题3，不复制正文 |
| 资料不够时怎么办 | 当前输入与继续执行的判断 | Context、Loop；主题5、6。补查、澄清是条件路径，不编造已发生原因 |
| 怎样形成分析与卡片 | 模型按规则整理；界面呈现结果 | 已有Skill及五张分析卡片；主题9。逐字段和真实结果待核验 |

**这一入口的主正文是主题9。** Skill解释引用主题4；查询引用主题3；运行支撑按需要引用主题5–8、11。

这项业务不是“把查询结果换个说法”。课程要求分析购买意向、感兴趣产品、未成交原因、竞品及跟进建议；事实不足时不能补造结论。

### 功能三：合同生成

**过程：明确订单 → 查询合同资料 → 核对缺项和模板 → 按配置审批并生成 → 复核文件。**

| 过程中的问题 | 进入哪个支撑机制 | 云帆具体技术与原正文 |
|---|---|---|
| 合同任务按什么方法做 | Skill中的任务说明与模板规则 | `order-contract-generation`；主题4、10合同段 |
| 订单、客户资料怎样取得 | 复用查询机制与数据权限 | 合同数据查询Tool、CRM服务；主题3、11 |
| 什么时候允许生成 | Tool配置、人工审批、中断续接 | `interrupt_on`、LangGraph resume、Checkpoint；主题7、11 |
| 谁产生Word文件 | 受控文件工具与模板处理 | Word模板生成工具；主题10合同段。Skill本身不执行替换 |

**这一入口的主正文是主题10“合同”段。** 与月报分开进入，但原文不重写。

字段真实性、模板适用性、完整生成结果仍待核验。生成文件不等于发送合同、签约或更新订单；人工复核是教学要求，不假称本轮实测。

### 功能四：销售月报

**过程：明确月份和范围 → 取得统计 → 组织分析 → 展示和保存报告。**

| 过程中的问题 | 进入哪个支撑机制 | 云帆具体技术与原正文 |
|---|---|---|
| 数据按什么口径统计 | 确定性业务查询与统计规则 | 月报统计Tool及业务代码；主题10月报段 |
| 报告怎样组织 | Skill规则、模型使用统计返回 | `sales-monthly-report`、Context；主题4、6、10月报段 |
| 等待时怎样知道进度 | Todo与流式事件展示 | TodoListMiddleware、运行事件；主题8。是否实际使用以任务证据为准 |
| 结果怎样交付 | 报告展示与文件保存 | 已有报告展示/保存能力；主题10月报段。保存控制按具体Tool核对，不能套用合同审批结论 |

**这一入口的主正文是主题10“月报”段。** 合同重模板字段，月报重统计口径；共享运行机制，但不共享同一套交付标准。

统计结果、目标值来源与报告解释仍需核对，不能把报告生成成功当作内容准确。

## 三、支撑机制共用一份，技术挂在对应机制下

### 支撑机制怎样分组

| 共用机制组 | 解决什么问题 | 原正文入口 |
|---|---|---|
| 任务理解与规则 | 模型看见什么、这项业务按什么要求做 | 主题6 Context；主题4 Skill |
| 行动与继续执行 | 请求怎样执行，结果回来后是否继续 | 主题3 Tool；主题5 Loop |
| 状态与续接 | 保存哪些中间信息，暂停以后怎样继续 | 主题7 State/Checkpoint/Memory |
| 进度与过程展示 | 用户怎样知道任务正在做什么 | 主题8中的Todo和流式展示 |
| 控制与异常 | 什么可做、什么需审批、什么应停止 | 主题11；联动主题3、5、7 |

**Harness 是观察这些运行职责的整体视角。** 不把业务服务、数据库、所有产品决策都硬塞进 Harness 的子树，也不把 DeepAgents 当作唯一可能实现。

### 机制怎样落到具体技术

| 机制 | 已有工程对应 | 技术边界 |
|---|---|---|
| 模型调用与工具循环 | DeepAgents、LangGraph、AgentRuntime | 不等同于固定Plan–Execute–Reflect状态机 |
| 工具执行 | Python StructuredTool、Next工具接口、CRM Service | 模型提请求，服务执行；权限校验仍有身份缺口 |
| 任务说明的发现与读取 | ManagedSkillsMiddleware、Skill元数据、`SKILL.md` | 不把所有Skill全文每次都装入模型输入 |
| 当前输入与长度处理 | 消息及各输入来源、框架默认摘要中间件 | 不是项目自研精细裁剪器；某次摘要触发未证 |
| 状态快照与审批续接 | LangGraph State、SqliteSaver、interrupt/resume | 保存运行状态不等于业务回滚或任意故障可恢复 |
| 长期信息加载 | ManagedMemoryMiddleware、`MEMORY.md` | 不等于CRM数据库；不要求每个业务主动写记忆 |
| 任务进度展示 | TodoListMiddleware、流式事件 | 进度可见不证明任务正确，不等于完整Trace |
| 文件交付 | Word模板工具、报告展示/保存能力 | 文件能产生不等于内容已通过业务验收 |

一个具体技术可能支撑多项机制。例如 LangGraph 涉及循环、状态与审批恢复，所以可以从多处引用；不要求它在树上只能出现一次入口。

### 两条跨层支线不能丢

**产品判断支线：**做哪项功能 → 是否需要Agent → 用什么验收标准 → 对照效果与成本。沿用主题12，面试转入L4；不是运行系统里的一个组件。

**证据支线：**功能、过程、机制、技术都各自关联来源。课程图、代码链、UI观察、教学走查与实际效果分别保留证据身份；底层有代码，不自动证明上层业务已成功。

## 五、整个模块的覆盖边界

### 当前已经形成正文的核心范围

| 范围 | 讲到哪里 | 尚不能据此宣称什么 |
|---|---|---|
| 业务功能 | 查询、客户分析、合同、月报的机制解释 | 不是CRM全部业务或全部Skill的完整教材 |
| 整体运行 | 模型、框架、工具、原业务服务的分工 | 不是所有Agent架构的统一标准 |
| 单主Agent机制 | Tool、Skill、Loop、Context、State、Checkpoint、Memory | 不是所有机制都在每个任务中被触发 |
| 进度与人工控制 | Todo、流式展示、数据范围、审批、暂停续接 | 不是完整分布式追踪、自动补偿或生产安全验收 |
| 功能验收与面试 | 方案选择、事实准确、耗时、成本、采用及11个短答案 | 没有实际提效、成交提升或个人贡献的完整证据 |

以上“有正文”是内容覆盖状态，**不是工程已实现、实际运行通过或用户已验收的同义词**。
