## L3｜功能具体怎样实现

### 1. 先看整体分工

**模型决定接下来做什么；运行框架把请求接起来；业务服务负责真正查、改数据。**

| 谁 | 在云帆中负责什么 |
|---|---|
| 模型 | 理解需求，提出查询或执行请求，整理回答 |
| Agent 运行框架 | 调用模型、分派工具、收回结果、保存状态、处理审批中断 |
| Tool | 提供有名称、有参数的查询或操作入口 |
| 原 CRM 业务服务 | 检查权限、数据范围和业务规则，再访问数据库 |
| CRM 界面 | 展示回答、调用过程、分析卡、任务进度或文件 |

**老师怎么画：**基础术语课 p33，把 AI 模型与“知识库查询、流程控制、数据接口/MCP、上下文存储”放进同一个智能体框。通俗理解：除了模型，还要有让应用取资料、控制执行、保存信息的能力。

这张组成图不要求每个 Agent 配齐所有模块；其中提到 MCP，也不证明当前客户分析通过 MCP 查询。

**云帆对应：**请求从 CRM 界面经 Next.js API 进入 Python AgentRuntime；DeepAgents 创建主 Agent，CRM Tool 再回到原 CRM 服务。它是一条已有代码链，不是本稿新运行的 Trace。

来源：基础术语课 p33；主审计 §3.1–3.3；定向核验 §1。〔课程1、工程1、工程2〕

### 2. Harness、DeepAgents、LangGraph 分别是什么

**Harness 可以理解为：让模型在应用里受控做事的一套运行支撑。**

老师 Harness 上 p6 用 Model、Harness 结构、外部能力说明 Agent 的组成。本稿借这个视角，依次看工具、循环、输入信息、状态和控制；它不是新的知识父子树，也不包办 CRM 的全部业务功能。

| 名称 | 怎么记 | 本项目依据 |
|---|---|---|
| Harness | 看运行支撑的职责 | 课程的解释视角，不要求单独安装一个同名软件 |
| DeepAgents | 项目选用的具体 Agent 框架 | 审计版本 0.7.7，调用 `create_deep_agent()` |
| LangGraph | 承担底层图执行与状态持久化等机制 | 审计版本 1.2.11，项目使用 SQLite Checkpoint |
| LangChain | 模型、工具等基础组件的相关库体系 | 审计版本 1.3.15；不与前两者当作同义词 |

**为什么这点要学：**面试问“用什么搭建”，回答 DeepAgents；追问“怎么运行”，再讲工具循环、状态和审批。只报框架名，不能解释产品机制。

项目没有留下足够材料证明当时如何比较所有替代框架；可以分析当前选择的好处，不能补写“当时经过实验最终选定”的经历。

来源：Harness 上 p6；P1-B1 收尾 R006；主审计 §2、§3；定向核验 §1。〔课程2、研究1、工程1、工程2〕

### 3. 查询：模型怎样读到真实 CRM 数据

**模型发出查询请求，系统执行查询，再把结果交回来。**

一条 CRM 查询分四步：

1. 模型提出调用某个查询 Tool，并给出参数。
2. Python 工具把请求送到 Next.js 的工具接口。
3. 接口检查权限，原 CRM Service 按业务规则取数据。
4. 查询结果返回运行图，供后续模型调用使用。

Service 是放业务规则的代码层；Repository 是连接数据存储的代码层。这里不是让模型直接拼任意 SQL 查库。

| 查询对象 | 已有工程规则 | 对学习者意味着什么 |
|---|---|---|
| 线索 | 可按负责人限制范围 | “有这个客户”不代表当前销售能看到 |
| 沟通记录 | 通过关联线索判断数据范围 | 不能因为用户说“查全部”就越权 |
| 订单 | “仅自己”范围通过线索负责人收紧 | 订单与客户的关联必须正确 |
| 商品 | 复用原商品查询服务 | 商品事实来自系统，不靠模型猜 |

**老师怎么讲：**Harness 上 p8 把工具信息放进模型可见输入，并画出调用、取得结果、继续处理。图里的“模型调用工具”是简写；实际代码由应用执行。

**产品取舍：**复用原 CRM Service，可以沿用原有规则，减少再写一套业务逻辑。但身份认证仍有审计缺口，不能把“复用权限”说成“全部路径已经安全”。

来源：Harness 上 p8；主审计 §3.1–3.2、§4、§7；定向核验 §1。〔课程2、工程1、工程2〕

### 4. Skill：同类业务怎样按同一套方法处理

**Tool 负责“能做什么”；Skill 说明“这类任务应该怎么做”。**

老师 Skill 课 p4–5，用“提示词＋工具＋工作流”的封装解释能力复用；p6 讲按需读取，避免把所有内容一次塞给模型。这是课程的说明方式，不意味着每份 Skill 都自带可执行工具。

云帆把六份已启用 Skill 的元数据交给运行框架。模型能看见技能索引，具体 `SKILL.md` 正文按运行需要读取；不能说六份全文每次都进入模型输入。

| 业务 | 任务说明 | 真正执行依靠什么 |
|---|---|---|
| 客户分析 | `crm-lead-analysis` | CRM 查询、模型整理、分析卡展示能力 |
| 合同生成 | `order-contract-generation` | 订单合同数据查询、Word 模板及生成工具 |
| 销售月报 | `sales-monthly-report` | 统计工具、模型组织内容、报告展示与文件能力 |

**关键边界：**Skill 不是另一个独立 Agent，也不是一段读完就必定成功的程序。任务说明要求“按规则做”，仍要检查模型是否选对工具、参数是否正确、输出是否满足要求。

来源：Skill 课 p4–6（QC020–021）；主审计 §5.2；定向核验 §1–2。〔课程3、工程1、工程2〕

### 5. Loop：为什么查完以后可能还会继续查

**拿到结果后，模型再决定：继续取资料，还是已经可以回答。**

Harness 上 p16 的图包含：读取目标与状态、规划、调用工具、检查结果、判断完成或继续。它解释一种运行机制，不代表所有请求必须完整走过同样的步骤。

在云帆，DeepAgents/LangGraph 有“模型—工具—模型”的执行路径。简单问题可以直接回答；需要客户事实时可以查询；拿到结果后可以继续调用，也可以结束。

**保留已有 UI 观察：**10-15 交接记录转述，用户曾看到“读取文件 → 查询线索 → 查询沟通记录 → 查询订单 → 再次查询沟通记录 → 生成分析”。

这个顺序保留在此处，不再压缩成四项冒充完整记录。但它只证明用户看到了这些界面动作：

- 读取的文件是否是 Skill，待原日志确认。
- 再查沟通记录的原因，待原日志确认。
- “生成分析”是否对应单独工具，不能只看标签判断。

不能写成“第一次资料不足，因此二次查询”。也不能把模型内部思考当作可见的执行证据。

来源：Harness 上 p8/p16；定向核验 §1；10-15 交接档案 §6.5。〔课程2、工程2、观察1〕

### 6. Context：这一次模型究竟看见什么

**Context 就是这一次模型调用收到的信息。**

查询结果回来后，只有进入模型输入，才能成为本次回答的直接依据。数据库里存在某条记录，不代表模型已经看见它。

老师 Harness 上 p14，把系统提示词、对话历史、工具定义、技能索引经过选择、裁剪、排序后，送入模型 API。

云帆已确认的输入来源包括：系统提示词、会话消息、可用工具描述、Skill 索引、加载的 Memory，以及实际调用后返回的工具结果。不同来源进入的条件不同，不能假定每轮全部加载。

**输入也会变：**查订单之前，模型可能还不知道订单；结果返回以后，后续调用才能使用它。权限账号信息还会以框架运行参数传给工具，它不等于模型看到的自然语言信息。

**长度管理：**安装版本的 DeepAgents 默认带摘要中间件；没有发现项目自研的精细裁剪器。本轮没有证据说明某次客户分析触发过摘要，或最后究竟保留了哪些消息。

来源：Harness 上 p14（QC005）；定向核验 §2。〔课程2、工程2〕

### 7. State、Checkpoint、Memory：分别保存什么

| 名称 | 一句话理解 | 云帆对应 |
|---|---|---|
| State | 任务运行时保存的当前情况 | 线程中的消息、Todo、中断等 |
| Checkpoint | 把某个时点的运行状态存下来 | LangGraph 的 SQLite 状态快照 |
| Memory | 留给后续使用的信息 | 本项目加载的 `MEMORY.md` 长期信息 |
| Context | 这一次交给模型看的信息 | 从消息及各输入来源组成的模型请求 |

**怎样配合：**任务运行更新 State；Checkpoint 保存线程状态；继续会话或审批恢复时按线程读取。Memory 可以被加载到模型输入，但它不等于状态快照。

老师 Harness 上 p16 解释 Run State，p20 画出记忆经过检索、过滤、排序后进入 Context。课程并未在这两页独立解释 Checkpoint；这里的 Checkpoint 机制来自项目核验及既有框架研究。

审计确实发现了 Checkpoint 数据和 `SqliteSaver` 代码，不能写成“未实现”。但有快照也不能保证任意故障恢复成功，更不能自动撤销已写入数据库或已发送的消息。

**别混淆：**客户沟通记录是 CRM 业务数据；本项目的长期 Memory 是另一种用途。两者都可能供模型使用，但不是同一个东西。

来源：Harness 上 p16/p20；主审计 §5.5；定向核验 §1–2；收尾 R023。〔课程2、工程1、工程2、研究1〕

### 8. Todo、流式展示和多 Agent：哪些真的存在

**Todo 帮用户看任务进度；它不是成功证明。**

老师 Harness 上 p18，用 Todo Plan 表示目标拆解、执行检查和必要时调整。项目3 p2–3，把它用于等待较久的月报任务，让用户知道正在做什么。

云帆有 TodoListMiddleware，也会流式回传文字、工具状态、Todo 和业务卡片。流式展示解决“等待时看不见进度”，不能证明每个工具真的成功，也不等于完整分布式 Trace。

**三个不应夸大的地方：**

- 不能说每次简单查询都会先生成计划。
- 项目没有独立可观察的 Reflect 阶段；再次调用模型不等于通过质量审核。
- 项目隐藏并禁止 `task` 委派入口，没有可供业务调用的子代理协作；框架内部可能构造通用子代理，不等于项目已启用多 Agent。

来源：Harness 上 p18/p24/p25；项目3 p2–3；主审计 §3.3、§5.1；定向核验 §1。〔课程2、课程5、工程1、工程2〕

### 9. 生成客户分析：从查到事实到形成建议

**客户分析的价值，是把分散资料整理成有依据的判断。**

老师项目2 p3–4 说明：只会查数还不够，要按规则分析。课程要求输出五项：

1. 购买意向如何。
2. 感兴趣的产品是什么。
3. 未成交的原因是什么。
4. 是否提到竞品。
5. 后续怎样跟进。

**云帆对应：**工程审计确认 `crm-lead-analysis`，可结合线索、沟通、订单、商品查询，输出五张分析卡片。五项课程模板与五张卡在整体用途上对应，但卡片逐字段约束及一次实际结果仍待核验。

教学走查可以这样理解：**查询事实 → 模型依据任务说明整理五项分析 → 展示结果。** 这是已有组件的讲解，不是声称本次跑过这条完整路线。

**产品边界：**“没查到未成交原因”与“客户嫌贵”是两件事。建议学习者把已知事实、分析判断、缺失信息分开；这是输出规范建议，不是声称当前系统已强制逐项做到。

本稿不填造客户记录、购买意向或跟进话术。要把教学走查升级成已验证案例，还需要查询结果、最终卡片及人工核对。

来源：项目2 p3–5；FeatureList 2.0 A2-1；主审计 §5.2。〔课程4、需求1、工程1〕

### 10. 同样是生成，合同和月报为什么做法不同

#### 合同：重点是按模板准确填数据

老师项目3 p3 讲的是：读取订单与客户数据，使用规定的 Word 模板，替换内容并生成文件。课上提及模板经过法务审阅，是老师的演示语境，不证明云帆本地模板已得到实际法务审核。

**工程已有：**合同 Skill、订单合同数据查询、Word 模板生成工具。现有主审计不足以确认所有合同字段和模板都适用于实际签署；财务/服务字段的真实性与模板适用性，仍待原项目 Codex 核验。

**教学走查：**确定订单 → 查询合同数据 → 核对缺项 → 请求生成并按配置审批 → 生成 Word → 人工复核。具体运行顺序、模板版本及真实生成结果仍待原项目 Codex 核验。

这里模型负责选择与组织步骤，Word 工具负责产生文件；Skill 本身不会执行模板替换。也不能把“生成合同文件”当作“发送合同、签约或修改订单”。

来源：项目3 p3–5；FeatureList 3.0 A3-2；主审计 §5.2–5.3；功能审计 SKL-005、TOL-010/011（符号与路径可读，中文损坏限制见附录）。〔课程5、需求2、工程1、工程3〕

#### 月报：重点是统计口径和报告解释

老师项目3 p2–3 讲的是：读取多项业务数据，按规则生成 HTML 月报，并用 Todo 展示长任务进度。

**工程已有：**月报 Skill、月报统计 Tool、报告展示与保存能力。统计在业务代码中完成；模型负责组织解释，不应靠它临时猜数。

**教学走查：**确定月份与范围 → 取得统计数据 → 按规则组织报告 → 展示和保存。现有材料未提供可验的完整月报运行记录；报告中的统计值、目标值来源、模型解释仍要逐项核对。

**和客户分析的差别：**客户分析围绕单个客户的情况；月报围绕一段时间的业务统计。它们共用工具调用、Context、状态和 Skill，任务规则与输出验收标准不同。

来源：项目3 p2–5；FeatureList 3.0 A3-1；主审计 §5.2；功能审计 SKL-004、TOL-008/009。〔课程5、需求2、工程1、工程3〕

### 11. 权限、审批和失败：系统何时应该停下来

**“能调用”不等于“可以随便做”。**

老师 Harness 上 p22，将动作分为通过、人工审批、禁止，并提出最小权限。云帆的 CRM 查询走角色与数据范围校验；新增、修改、删除等操作按配置触发人工审批。

**审批怎样接回任务：**运行图先中断，用户批准或拒绝后，通过 LangGraph resume 继续。Checkpoint 为状态续接提供基础，但不会代替业务校验。

| 遇到的问题 | 产品上应怎样处理 | 当前证据 |
|---|---|---|
| 客户或订单不明确 | 先澄清，避免查错或生成错文件 | 教学设计要求，非本次实测 |
| 没有权限 | 拒绝该数据路径，不换方式绕过 | CRM 代码有权限校验；身份边界仍有缺口 |
| 查询失败 | 说明缺少什么，再判断能否安全重试 | 有异常处理路径；未发现统一 Tool 重试/熔断策略 |
| 需要写入或生成受控文件 | 按当前 Tool 配置审批，拒绝后不执行该动作 | 已有中断/恢复及自动化测试；完整路径仍需核对 |
| 操作结果不明 | 先查是否已经成功，避免重复执行 | 幂等与补偿是后续设计要求，不能称为已全部实现 |

**重要限制：**审计发现客户端可控账号头、Python API 认证、审批票据及统一审计等问题。现有保护值得讲清，但尚不足以证明生产安全。

来源：Harness 上 p22；主审计 §3.3、§5.3、§7；定向核验 §1。〔课程2、工程1、工程2〕

### 12. 判断这个功能值不值得做

**先比较能否用更简单的方法完成，再验证 Agent 多出来的价值。**

| 任务特点 | 可以优先考虑什么 | 为什么 |
|---|---|---|
| 只查固定字段 | 普通查询或固定流程 | 步骤明确，通常更容易测试 |
| 数据齐全、只需改写表达 | 直接模型调用 | 未必需要多轮取数据 |
| 需根据结果决定补查什么 | 受控 Agent | 有动态选择下一步的需求 |
| 合同字段和模板稳定 | 规则校验＋模板生成，可由 Agent 调度 | 不需要为了自主性把确定步骤都交给模型 |

老师 Harness 下 p2 比较预设路径与动态行动，也提出混合方式。因此固定 Workflow 与 Agent 可以组合，不是只能二选一。

**本模块只保留必要的验证问题：**

- 客户分析：事实是否有依据，建议是否可执行。
- 合同：字段与模板是否正确，是否需要人工修订。
- 月报：统计口径是否一致，文字是否曲解数据。
- 共同指标：完成时间、失败率、人工修订、Token 用量与用户采用。

这些是待实施的验证设计。项目已有工程自动化测试，没有正式任务黄金集、可归因的销售提效或成交提升数据。

Token 是用量，不是金额。工程已有 usage 采集，没有价格表、费用金额、预算和限额执行的完整证据；FeatureList 5.0 的“Token统计与限额”是需求，不能据此写成全部落地。

来源：Harness 下 p2；主审计 §5.4、§8；定向核验 §4；FeatureList 5.0 B5-2；岗位分析 §3/6。〔课程6、工程1、工程2、需求3、岗位1〕

## L4｜项目面试实战

下面是本项目的练习答案，不代替个人贡献记录。实际说“我做了”之前，须确认由自己完成或主导的工作。原题、可信度和证据在附录对照。

### 1. 为什么用 Agent，固定流程不行吗？

“如果每次只是查固定字段，我会优先用固定流程。只有客户情况需要根据结果继续补查时，Agent 才可能更合适；云帆还没有做正式对照实验，所以我不会说它一定优于固定流程。”

记住：**是否要动态补查。** 追问：怎么设置同一批任务做对照？〔面1〕

### 2. 比起原 CRM，这个 Agent 多了什么？

“原 CRM 让销售分别查客户、沟通和订单，Agent 把取数据和整理分析接成一个任务。项目还支持合同和月报，但这些增量有没有真正省时间，目前缺实际采用和工时数据。”

记住：**从分别操作，到任务交付。** 追问：哪些场景保留原页面更好？〔面2〕

### 3. 你们的 Agent 到底怎么搭的？

“云帆用 DeepAgents 搭主 Agent，由模型提出下一步请求，工具执行后把结果交回来。底层用 LangGraph 管理运行状态和审批恢复；当前没有启用业务子代理，也没有单独的反思节点。”

记住：**框架、工具循环、状态。** 追问：Harness 和 DeepAgents 有什么区别？〔面3〕

### 4. 为什么不让模型直接查数据库？

“CRM 已经有权限和业务校验，所以项目让 Tool 调原有 CRM 服务，再由服务访问数据库。这样能沿用现有规则，但当前身份认证仍有缺口，正式上线前必须补齐。”

记住：**复用业务规则。** 追问：如果工具直接绕过 Service 会怎样？〔面4〕

### 5. Skill 和 Tool 到底有什么区别？

“Tool 是可执行入口，比如查订单、生成 Word；Skill 是这类业务的操作说明。客户分析和合同使用不同 Skill，但共用 Agent 运行机制，不是每加一个 Skill 就多一个 Agent。”

记住：**说明怎么做／真正去执行。** 追问：读了 Skill 为什么仍可能做错？〔面5〕

### 6. 重复查询沟通记录，是不是在反思？

“目前只能确认用户在界面看到再次查询，原因还没拿到原始调用记录。重复查询可以发生在工具循环里，但不能直接说第一次不足，也不能说系统执行了独立反思阶段。”

记住：**看到动作，不等于知道原因。** 追问：你需要什么证据判断原因？〔面6〕

### 7. 执行到一半失败怎么办？

“先查哪一步失败、是否已经产生写入等影响，确认可以安全重试再重试。缺关键信息就明确说明，涉及权限或写入则停下来交给人；项目没有统一自动补偿，不能承诺所有失败都能恢复。”

记住：**查状态、控副作用、再决定。** 追问：用户重复提交会不会重复生成或写入？〔面7〕

### 8. 有 Checkpoint，是不是就能保证恢复？

“Checkpoint 保存运行状态，让继续会话和审批恢复有基础。它不会自动撤销已经提交的业务操作，也不能单靠有快照就证明所有故障都能恢复。”

记住：**保存状态，不保证业务回滚。** 追问：State 和 Context 为什么不是同一个东西？〔面8〕

### 9. 怎么证明输出可靠、真的帮销售提效？

“我会用同批任务比较人工、固定流程和 Agent，核对事实准确、完成时间、修订量和成本，再看销售是否采用。云帆目前有工程测试，没有这套完整业务效果实验，所以我不会报提效数字。”

记住：**质量、时间、成本、采用。** 追问：模型准确率提高，业务仍没改善，查什么？〔面9〕

### 10. 合同和月报，为什么不都让模型自由生成？

“合同要守住模板和字段，月报要守住统计口径，确定性部分交给业务代码或文件工具。模型负责理解和组织，不代表可以改条款或猜数字；合同字段和模板是否满足实际使用，仍需核验。”

记住：**模型组织，规则守底。** 追问：文件能下载，算任务成功吗？〔面10〕

### 11. 如果现在要上线，最先补什么？

“我会先补可信身份和关键操作的审批、审计边界，避免读错人或执行不该执行的动作。然后用固定任务集检查质量、耗时和成本；现有单机工程还不能直接当成生产系统。”

记住：**先安全可控，再证明效果。** 追问：哪些问题宁可不上线也不能放过？〔面11〕

### 保留的 Agent 七字段短读

这是一份可复用的选读内容，入口可来自 L2 或 L3；不进入 L1。

1. **一句话定义：**Agent 以模型为核心，能按任务决定下一步，并在需要时调用工具完成任务。这里限定本模块的 LLM Agent，不覆盖所有历史智能体定义。
2. **Why：**销售需要的不只是文字建议，还要基于真实 CRM 资料完成分析或交付。
3. **原理 → 项目落地：**课程把模型与应用能力放在一起；云帆用 DeepAgents 接模型、Tool、Skill 和状态，具体分工见 L3.1–4。
4. **关键边界：**能受控选择下一步，不等于无限自主；模型也能做判断和规划，工具不是每次必用。
5. **Case：**客户分析、合同、月报共用同一 Agent 知识；三者的任务规则与证据分别保留。
6. **Interview Lens：**“比直接问模型多什么？”——“在云帆里，它还把 CRM 查询、文件能力和运行控制接起来，实际动作受业务规则约束。”
7. **Evidence：**基础术语 p33、Harness 上 p6/8/16；主审计 §3/5；定向核验 §1–2。定义是本模块的通俗整合表述，不是老师原话或行业唯一标准。
