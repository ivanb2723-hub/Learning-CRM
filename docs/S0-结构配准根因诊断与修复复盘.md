# S0 System Overview｜结构配准根因诊断与修复复盘

> 记录日期：2026-10-04。范围仅为 S0 的四域主体、中央 Core 与共用底座的视觉配准。A Layered View、五张原始主体资产、风格和知识数据不在本报告的修改范围内。
>
> 本文区分 **代码/素材可核实的事实**、**浏览器画面的观察** 与 **尚需用户验收的判断**。工程测试通过不等于视觉高还原通过。

## 1. 结论先行

先前反复改错的根因不是一个孤立的 `x/y` 数值，而是**将三种不同几何对象混作同一个盒子**：React Flow 的逻辑 Node 盒子、透明图片的绘制盒子、以及模块真正接触底座的视觉 footprint。底座也有外层轮廓与内层承载面之分。用前两种盒子的中心去对齐整个底板，无法保证第三种 footprint 落在斜视承载面内。

黄色 Business 已基本正确是一个**已经单独校准过的实例**，不是上述盒子定位方法正确的证据。其余三域的接地点、分布与前缘关系不同，套用“居中＋缩放”的直觉会同时产生偏位、出界、悬浮或过度缩小。Core 另外涉及源素材自带底板、中央空腔前缘的遮挡顺序和额外投影，不能仅用节点中心解决。

上轮将 S0 校准约束改为“主体落点位于各自的内层承载四边形、前缘不穿出、同时维持参考图的大致主体占比”，并移除了 Core 的额外 CSS 投影。但这**尚不是参考图逐像素重合认证**；用户视觉验收仍是最终标准。

## 2. 可追溯的输入与渲染链

- 正确结构参考：本地原始文件 `正确S0.png`，实际尺寸 **1028 × 768**。旧的 `design-qa.md` 将它写成 `1000 × 768`，这个尺寸记录不准确。
- 共用 S0 Fabric：`src/assets/system-atlas/system-fabric-s0.webp`，1487 × 1058；它已经包含四域外底板、内承载面、中央空腔、十字通道与局部阴影。它不是五个可独立移动的底座。
- Domain 图片：Business、Resources、Capability、Runtime 均为 1536 × 1024；Core 为 1333 × 1180。五张图片保持原样。
- React Flow 使用 1440 × 940 的图坐标。Fabric 由 `AtlasStructureLayer.tsx` 放在 `(148, 50)`，渲染尺寸 `1140 × 810`；五个逻辑 Node 的位置和 S0 视觉偏移由 `atlasViewModel.ts` 给出。
- `AtlasAssetNode.tsx` 把每张图放在对应 Node 内；CSS 使用 `object-fit: contain`，再以 `translate(x,y) scale(s)` 绕指定 `visualCenter` 变换。`visualCenter` 是变换原点/估计值，**不是自动识别出的实物重心或地面接触面**。
- Governance 是另一个低权重斜向 SVG 层；Core 前缘另有一段从原 Fabric 截取的置顶图像，用于处理中央空腔的遮挡。两者不能当成 Domain 的定位基准。

因此实际链路是：

```text
React Flow logical position / Node box
  → img contain 后的真实绘制区域与 letterbox
  → 透明资产内部的可见主体及接地点
  → S0 独立绘制的 Fabric 内层承载面
  → 前缘遮挡、投影与 Governance 叠层
  → 浏览器最终画面
```

以前的调整经常只检查链路的第一、二步，没有验证第三、四、五步。

### 当前 S0 配准依据一览

| 对象 | React Flow 逻辑位置 | Node 盒子 | 当前 S0 `translate x/y; scale` | 真正应对齐的对象 |
|---|---:|---:|---:|---|
| Business | `(510,18)` | `430×290` | `(-12,+50); 0.80` | 橙色内承载面；本轮冻结 |
| Resources | `(70,312)` | `430×290` | `(+149,-44); 0.76` | 左侧蓝绿内承载面及设备接地点 |
| Capability | `(930,322)` | `430×290` | `(-136,-41); 0.68` | 右侧紫色内承载面及分散模块接地点 |
| Runtime | `(500,575)` | `430×290` | `(+12,-106); 0.69` | 下方绿色内承载面及长条主体/外围设备接地点 |
| CRM Core | `(610,350)` | `300×245` | `(-40,-45); 0.91` | 中央空腔、十字连接臂与前缘 |

这些数值是当前实现状态，不是从参考图提取出的五组完美真值。图片盒子仍承载 React Flow identity；可见主体的位置由盒内变换决定。四域图片与 `430×290` 盒子的长宽比接近，`contain` 的垂直留边约 **1.7 图坐标单位/侧**；Core 的横向留边约 **11.6 单位/侧**。因此 letterbox 必须计入换算，但三域的大偏差并非主要由这 1.7 单位造成。

## 3. 为什么 Business 能对，而其他对象反复不对

### Business：成功是特例，不是通用算法的证明

Business 在用户给出的对比图中已经基本正确，因此本轮锁定其偏移和比例。其橙色区域、主体群组和现有 `(-12,+50,0.80)` 组合达到了可接受的视觉嵌套。先前我说“它因为素材更规整、透明留白更对称，所以按盒子对齐也会成功”，**这个说法证据不足**。

对源图做 `alpha > 128` 的像素外框检查：Business 为 `(187,79)–(1424,954)`，Resources 为 `(226,109)–(1294,875)`，Capability 为 `(176,103)–(1408,908)`，Runtime 为 `(99,85)–(1458,939)`。Business 的可见像素外框并不比其他素材更接近画布水平中心。况且像素外框包含建筑立面、发光及悬空部分，不是地面 footprint。**已确认的是 Business 这组特定参数有效；不能把“留白对称”当成已证实根因。**

### Resources：盒子中心与设备落点不是同一个中心

左侧区域内有圆柱体、竖向机柜、小盒和连接线；它们的上沿、可见外框、地面落点并不共用一个矩形中心。此前把图片/Node 的中心放到左大底板中央，忽略内层蓝绿承载四边形及靠近中央通道的斜边，导致右前部小设备有越出或“挂在桥上”的观感。只缩小会让它退得过远、无法填充承载面；只平移则会让另一侧越界。

修复依据改为四个实际模块接触点在左侧内层四边形内，同时检查左右占比和前缘，而非让整张透明图的 bbox 居中。当前 `(+149,-44,0.76)` 是这组约束下的落位；它不表示 Resources 的 source canvas 中心恰好对应底座中心。

### Capability：分散模块放大了斜边误判

紫色主体有中心芯片、数据库/小终端和外围连接件。视觉最高点与最左、最右接地点分离；对全图做矩形居中，容易让某些外围模块压到右侧平台的前缘或内侧通道。先前曾试图兼顾“占满平台”和“不穿斜边”，但没有先区分外围立面与实际地面接触点，导致忽大忽小、忽左忽右。

当前按紫色**内层承载面**以及接触点约束为 `(-136,-41,0.68)`。较小的比例不是为了整体缩小来掩盖问题，而是当前既定素材与这块斜视承载面在**统一等比缩放**条件下可容纳的范围；若认为它相对参考图仍显小，需要重新测量参考图的内承载四边形与源资产的真实接触 footprint，不能直接再放大。

### Runtime：长条主体的“视觉居中”尤其容易骗人

绿色区域是横向设备列＋四周小设备/管线，长宽与重心和底板外轮廓并不一致。其最前接地点与主体几何中心相距较远。此前按整图或长条主体中心移动/缩放，会让右前外围设备跨过下方底座斜边；反向修正则显得整组内容往后缩、偏斜或悬浮。

当前把下方绿色内层四边形与四处接地点作为第一约束，再检查主体的水平展开和前缘，得到 `(+12,-106,0.69)`。这解决的是承载安全与中心趋势，**不等于**源素材内部物件布局会与参考图逐个重合。

### CRM Core：不仅是中心坐标，还有底座与遮挡关系

Core 的 source canvas 是 `1333×1180`，而它的可见外框、最下方底板、上方蓝色核心并不等价；`300×245` Node 内又有横向 letterbox。此前把 Core 的 Node/图像中心对齐到场景中心，忽视了 Fabric 已经绘制的中央凹槽与四向连接臂，出现“低矮底座放在凹槽上面”“四侧留空”或过度覆盖通道等不同症状。这里必须分别校准**水平中心**、**底板前缘接触高度**以及**遮挡层顺序**。

当前 Core 的视觉中心在图坐标 `x≈720`，前缘接点测试在 `y=505–515`，置于中央空腔前缘之后。需要注意：现有 Core 原图本身是低重心、无参考图中大号“CRM Agent”字样的多层底座；参考图 Core 更高、更有文字。冻结原素材时，仅靠平移和等比缩放无法消除这个**素材内容差异**。

## 4. Core → Runtime 白色/发灰残留的具体层源

这处现象不能笼统归为“坐标偏了”。代码里能明确找到两种额外贡献：

1. `system-atlas-milestone-a.css` 的通用 `.milestone-atlas-node__asset` 原本给所有图加 `drop-shadow(0 17px 15px …)`，hover/selected 又有更大的彩色投影。Core 原图已带自身接触阴影；叠加的 CSS 阴影会落在 Core 正下方的 Runtime 连接区。当前只对 **S0 Core**（含 hover/selected）设置 `filter: none`，A 不受此选择器影响。
2. `AtlasStructureLayer.tsx` 的 `.milestone-atlas-overview-core-rim` 位于 `z-index: 12`，把**原 Fabric** 的中央前缘再绘一次以压住 Core 底板。旧的裁切路径包含更宽的白色 V 形区域，产生类似半透明白片/前缘叠影的观感。当前裁切改为较窄的前唇 `M618 433 L720 508 L822 433 ...`。短暂隐藏整个前缘层会暴露 Core 底板更明显的白色尖角，因此没有把遮挡层整块移除，也没有另加白片。

Fabric 原图与 Core 原图自身也有白色实体/高光。它们是冻结资产内容，不应与额外 DOM 遮罩混为一谈。Governance 的斜向蓝色带横贯画面，不是白色局部阴影；默认 `.milestone-atlas-node__focus` 透明度为 0，也不是未选中状态的来源。**上述定位解释了额外的灰影和重复前缘；若浏览器中仍看到白色实体，不应声称已全部“清除”，应先区分原图实体与额外层。**

## 5. 之前为何给了参考和红蓝标注仍会改错

1. **参考图没有先被转换成统一坐标下的承载面与接触点。** 红蓝框表达了正确方向，但不是可以直接拿来作为所有图片 `<img>` 盒子的 `x/y/scale`。每张透明图内部主体的源坐标都不同。
2. **把“外层大板子”当成可占满的地面。** 底座的白色外 rim、蓝/紫/绿的内承载面、通道和中央空腔不应共享一个“可放物体 bbox”。这尤其会让前缘、桥边和 Core 附近穿出。
3. **把最高像素/可见 bbox 误当成接地 footprint。** 立面可以在斜视投影里跨过一条地面线，地面接触点却不能跨出承载四边形。仅看矩形重合会同时误判“偏小”和“越界”。
4. **缺少逐对象、同尺度的 overlay 验收。** 旧的 `qa/compare_atlas.py` 使用写死的缩放和平移，且引用的是早期截图；它不能证明当前浏览器画面与 `正确S0.png` 逐对象重合。先前 QA 把参数/测试通过表述为视觉通过，是过早结论。
5. **把 Core 的几何问题和层叠问题混在一起。** 继续挪 Core 无法消除额外 drop-shadow 或过宽的前缘覆盖；反过来加白色遮罩也不能使主体真正落位。
6. **冻结资产与参考图并非像素相同。** 参考图中部件高度、内部布局和中央文字，与现有五张独立透明资产有内在差别。持续微调 transform 不可能把不同内部画面变成同一张画面。这个边界应在验收里明确，而不是假装还能靠下一次 `x/y` 解决。

## 7. 当前验收状态与之后复核方法

**状态：S0 几何约束与工程回归通过；完整视觉一致性仍待用户验收。** 不应把本文写成“已与参考图完美重合”。上轮浏览器截图是即时可视检查，没有生成一套新的、在同一 viewport 下精确配准的五对象差异图；仓库 `qa/` 中早期 `*-final.jpg` 和基于它们的 overlay 不能冒充本轮最新证据。

若后续继续复核，先固定浏览器 viewport 与 React Flow viewport，等五张图全部加载和过渡结束；以 Fabric 四域内承载面和中央凹槽作为共同 landmark，对正确参考图做**统一等比**配准，再分别叠加 Business、Resources、Capability、Runtime、Core 的地面接触轮廓。每个对象至少检查：中心偏差、接触点是否在面内、前缘是否交叉、Core 底板是否被正确遮挡。Governance 只核对贯穿方向和低权重，不把它当第五个域。不要仅比较整个网页与裁切过的参考图，也不要沿用旧脚本的固定平移值。

若这套复核显示“接触点正确但形状仍明显不像参考”，先判定是否为**冻结资产与参考图内容不同**，不要继续用大幅缩放或白片遮盖来追求虚假的像素重合。若出现新的用户标注，优先把标注转成 source contact → target floor 的成对坐标，再动单个 S0 参数；不要牵连 Business 或 A。
