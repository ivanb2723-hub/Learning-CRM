# 云帆 CRM Agent 学习系统：前端现状核验答复

核验日期：2026-10-07。对应问题清单：`云帆CRM学习系统_Work前端核验问题清单_v1.0.md`。本文件是**现状审计**，没有修改前端、内容 Schema 或冻结的视觉资产。

核验方法：阅读当前实际入口、交互组件、内容数据、Schema 和校验器；在 `http://127.0.0.1:5173/` 以 1800×1100 浏览器视口实测 S0、S0-L、Core、Runtime Domain 与侧栏；执行现有测试、typecheck 和 build。此处的“已实现”只指当前主页面可用，不能把仅存在于 TypeScript 数据中的内容算作已经显示在网页上。旧称 **A Layered View** 在当前页面已更名为 **S0-L 系统分层**。

## 0. 总判断

1. **目前不能把已验收 Knowledge Card 仅作为数据填入、就在网页上正式展示。** 内容层已有较完整的 Zod Schema、H02/H06 示例及引用校验，但当前实际 UI 只渲染 S0 和 S0-L，没有 S1/S2 页面或 Knowledge Card renderer。
2. S0 与 S0-L 的视觉、双向切换、画布适应和 Core 点击是当前可用范围；“视觉锁定”是用户已确认的产品基线，不是代码里有一个自动锁定开关。
3. 四域是视觉/交互节点，不是内容库中每个 canonical Node 的可展开列表。点击 Runtime 只选中该图节点，不进入 Domain Focus。
4. 侧栏的案例追踪、知识索引、学习笔记是禁用按钮；S2+ 和 S3 也没有实际页面入口。
5. H02 在内容文件中已经有 `node:h02-context`、`card:h02-context`、课程/项目片段和 FAQ/RAG Case 路径，但目前是部分 Seed 数据，**不是已呈现的正式 Card**。
6. 正式 Card 的合理承载状态是拟建的 S2 Node Focus；目前没有这个页面，不能把 S0/S0-L 当成 Card 页面。
7. 今天最短落地路径是：保留 S0/S0-L → 一次性接通 canonical 内容库与 S1/S2 的入口和通用 Card renderer → 补全 H02 内容及来源 → 走测试与浏览器验收。不是只改一个 H02 文本文件。

状态归类：S0/S0-L **已实现**；内容 Schema、校验器、H02 Seed **已有但未接网页**；侧栏后续栏目 **仅视觉占位/禁用**；S1、S2、S2+、S3 **尚未实现**；打通数据与通用页面 **需要工程调整**。

## 2. Knowledge Card 前端容器与七点映射

**当前没有 Node Detail 页面，因此七点都没有固定的网页 UI 容器。** 下面“数据位置”只表示现有 Schema 可以承接，不等于已经渲染。不能把 S0 上的简短 Domain 注释误当作 Card 近似 UI。

| 冻结字段 | 当前实际数据位置 | 当前 UI 分类 | 导入时的最小处理 |
|---|---|---|---|
| 一句话定义 | `KnowledgeCard.definition` | 无固定 UI；**需要增加区块** | 通用 S2 renderer 展示。 |
| Why | `KnowledgeCard.why.course / industry / project` | 无固定 UI；**需要增加区块** | 渲染现有三层结构，避免合并成一个不明来源段落。 |
| 原理 → 项目落地 | `mechanism` + `projectUsage` | 无固定 UI；**需要增加区块** | 两段按现有字段呈现。 |
| 关键边界/易混淆点 | `boundaries[]`，每项含 `title/status/summary/sourceFragmentIds`；最多 3 项 | 无固定 UI；**需要增加区块** | 渲染列表与状态。 |
| Case | `caseSummary` | 无固定 UI；**需要增加区块** | 可显示 Card 内的小 Case；目前没有 Case ID 直接挂载字段。 |
| Interview Lens | Card 内 `interviewLens[]`；另有独立 `interviewQuestions[]` | **尚未实现 UI**；没有卡片区块/Overlay/Drawer/Tab/侧栏 | 先确定一个通用显示方式，并避免两个数据入口重复维护。 |
| Evidence | Card 内 `claims[].sourceFragmentIds`、`evidenceRefs[]`；另有全局 `evidence[]` 与 `sourceIndex` | **尚未实现 UI**；无可点击引用/来源列表/Drawer/Tooltip | 接通引用解析与可见来源展示。 |

Relation 在数据层有 `relations[]` 与 Card 的 `relatedNodeIds[]`，但当前 React Flow 传入 `edges={[]}`（`SystemAtlasMilestoneA.tsx:179-183`）；网页既没有 canonical Node 连线，也没有 Card 关系列表。S0/S0-L 的道路是视觉素材，不是 Relation 图。当前**没有正文 vs Overlay 的页面层级划分**，不能声称 Interview Lens 或 Evidence 已归某一种 UI 容器。

## 3. Node、Card、Source/Evidence 的真实 Schema

### 3.1 数据位置、格式、ID 与实例

- 作者维护的实际入口是 `content/authoringContent.ts`（TypeScript object，`satisfies ContentBundle`）；来源片段在 `content/sourceIndex.ts`（TypeScript object，`satisfies SourceIndex`）。不是 JSON、Markdown、MDX 或 API。
- Schema 分别在 `src/domain/content/schema.ts` 和 `sourceSchema.ts`，交叉引用校验在 `validateContent.ts`；`src/domain/content/content.ts:1-8` 把两份数据校验后导出。
- canonical H02 Node：`id: 'node:h02-context'`、`slug: 'h02-context'`、`name: 'Context'`、`primaryDomainId: 'domain:harness'`、`summary: '为当前模型调用装配提示词、历史、工具信息与必要资料。'`（`authoringContent.ts:23`）。有统一 `nodeId` 规范，Card 用 `nodeId` 关联 Node。
- 当前前端图节点却是 `business-product / resources-infrastructure / capability / agent-runtime / crm-core` 五个视觉 ID（`atlasViewModel.ts:59-77,125-223`），**不是** `node:h02-context` 等 canonical ID。这是“内容已建模而网页未接通”的直接证据。

### 3.2 Card 的现有真实字段

`KnowledgeCardSchema`（`schema.ts:103-163`）实际定义：`id, nodeId, title, definition, reviewStatus, claims[{claimId,text,sourceLayer,sourceFragmentIds}], why{course,industry,project}, mechanism, projectUsage, boundaries[{title,status,summary,sourceFragmentIds,boundaryRevision?}], caseSummary, interviewLens[{question,answerFocus,sourceFragmentIds}], evidenceRefs[{sourceFragmentId,sourceLayer,note?}], relatedNodeIds`。这是已经存在的 Schema，**不是**“当前没有 Card Schema”；但没有对应的网页 renderer。Card 的 `id` 是 `card:h02-context`，Node 的 `id` 才是 `node:h02-context`。

### 3.3 Source/Evidence 对象的存在与消费

| 对象/字段 | 现状 |
|---|---|
| `sourceId`, `fragmentId`, `sourceType`, `location`, `text`, `relatedNodeIds` | 在 `sourceSchema.ts:3-37` 定义，`content/sourceIndex.ts` 有 4 条真实 Seed 片段；运行了校验测试，**网页未消费**。 |
| `claimId`, `claims[]`, `sourceFragmentIds[]` | Card Schema 与 H02/H06 数据中存在；校验器确保片段存在且来源层一致；网页未消费。 |
| `evidenceId` | 字段实际命名为全局 `Evidence.id`（如 `evidence:h02-course`），没有叫 `evidenceId` 的属性。 |
| `Evidence.target` | 类型允许指向 `node / case / question`，**不允许指向 claim**；当前 Seed 有 H02 Node 与 FAQ Case Evidence。 |
| `citation` | 没有独立 citation 对象/字段；当前 `sourceFragmentId + sourceIndex.location` 可作为未来引用的原料，但没有 UI。 |
| `claimType` | 没有；`claims[].sourceLayer` 表示来源层，不等于 claim 类型。 |
| `reviewStatus` | 只在 Card 层存在；Source、Fragment、Claim、Evidence 没有相应审核状态字段。 |

`SourceLayerSchema` 允许 `course / project / industry / inference / jd / interview` 六类（`sourceSchema.ts:3-10`）。这不能等同于已经实现 `course_fact / project_fact / jd_signal / interview_signal` 等精细标签；当前四条 Seed 片段只使用 `course` 和 `project`。

## 4. H02 — Context Assembly 导入可行性

1. **不改 UI，只填数据不能完整展示**：当前根本没有 S2。已有 H02 `definition/why/mechanism/projectUsage/caseSummary`，但网页没有消费。
2. 缺口同时包括内容与组件：现有 H02 只有 `Context ≠ Memory` 一条 boundary、一个 Card Interview Lens 问题、课程与项目两层来源；没有题目要求的 `Context ≠ System Prompt`、`Context ≠ Context Window`、五个 Lens 问题及 JD 片段。Schema 允许最多 3 条 boundaries、多条 lens 与 `jd` 来源，现有字段大体可承接；真正前端阻塞是 S1/S2 入口、通用 Card renderer、Source/Evidence 展示。
3. 最小文件范围：补内容改 `content/authoringContent.ts` 和 `content/sourceIndex.ts`；一次性前端接入会改 `src/App.tsx` 或 `SystemAtlasMilestoneA.tsx`（导航/状态）、增加通用 S1/S2 组件和样式，并在 renderer 中使用 `src/domain/content/content.ts` 的校验后数据。不是每张 Card 独立建页面。
4. **可以把 H02 作为第一张正式 Seed Card 的候选**，因为 canonical Node、Card、来源与关系已有基础；但现有 `reviewStatus: 'reviewed'` 不能替代用户对补齐后正文的验收，也不能声称现有 H02 已满足题目要求。
5. 目前不能被 System Atlas、S1、S2、Interview Lens、S3 同时在 UI 复用：Atlas 用视觉常量；后四个状态没有实现。内容库内部已可通过 `nodeId` / relation / case step 关联，但**“可关联”不等于“已在多页面消费”**。
6. 当前不是多个已上线页面各自写同一篇正文；是**一个尚未被主页面导入的 canonical 数据库 + 独立硬编码的 Atlas 视觉文案**。Card 的 Lens 与全局 InterviewQuestion 又存在两份问题数据入口，未来需定归属。

## 5. “Content ≠ Page” 的真实程度

内容**建模层面部分成立**：Node、Card、Relation、Case、InterviewQuestion、Evidence 通过 ID 关联，同一 H02 Node 可以出现在 FAQ/RAG Case steps，并有来源片段和 Evidence。`validateKnowledgeSystem()` 检查唯一性、缺失引用和部分来源层匹配（`validateContent.ts:211-295`）。

但**呈现层面未实现**：S1/S2/Interview Lens/Case Trace/Evidence 没有从 `content` 读取；`src/App.tsx` 与当前页面没有 import `src/domain/content/content.ts`。重复/分叉位置是 `atlasViewModel.ts:125-165` 的静态 Domain 文案与 `authoringContent.ts:10-40` 的 Domain/Node 数据；`authoringContent.ts:94,124` 的 Card 内 Lens 与全局 `interviewQuestions[]`；`caseSummary` 与独立 `cases[]`。它们不是自动同步的一份呈现内容。

## 6. 批量 Knowledge Filling 准备度

选择 **C：当前仍不能作为“只更新 Node 内容数据即可连续上线”的前端**。原因不是每个 Node 必须新写一个 React 页面，而是通用页面/renderer 根本还没有接入。现在新增 Card 即使通过数据校验，也不会出现在网页；也没有路由或 Domain → Node → Card 入口。一次性补齐接入后，已有 Schema 有机会支持后续数据驱动填充，不宜在那之前宣称 A/B 已达成。

所列后续对象的现状不同：H06 已有 reviewed 示例；C01/C10/C16 有 draft 占位 Card；H09、R10 有 Node 但无 Card；H05 **不在当前 `nodes[]` 中**。这只是当前文件核验结果，不对冻结 Node 清单作增删建议。若外部已验收卡片要求 H05，必须先按既定清单确认对应 canonical ID，不能默默写入一个不存在的 Node。

## 7. Review Status / 内容状态流

现有 Card `reviewStatus` 枚举仅为 `draft / lint-passed / reviewed / frozen`（`schema.ts:109`）；当前 H02、H06 为 `reviewed`，C01/C10/C16/R03 的占位 Card 为 `draft`。所问 `source_ready / fragment_ready / claim_ready / card_draft / review / verified` **均不是当前枚举值**。Boundary 另有 `frozen / candidate / revised / normal`，它不是 Card 的状态流。

网页不显示任何 Card 状态，也没有按状态控制 Card 可见性的逻辑。Schema 允许 frozen 与 draft Card 共存，但当前数据里没有 `reviewStatus: 'frozen'` Card，且没有“已冻结与生产中同时可见”的网页能力。H02 验收通过后是否设 `frozen` 应由内容流程决定；若定义为最终冻结卡，Schema 支持 `frozen`，但**设置该值现在不会使网页出现或改变可见性**。

## 8. Evidence 的实际挂载

- **Node/Card 级**：`card.evidenceRefs[]` 与全局 `evidence[].target: {type:'node', id:...}` 已支持片段来源；全局 Evidence 还可指向 Case 或 InterviewQuestion。
- **Claim 级**：`claims[].sourceFragmentIds` 可有 1–8 个片段，因此一个 Claim 能连多个来源片段；但这不是多个带独立 `evidenceId` 的 Claim Evidence 记录，`Evidence.target` 不能指向 Claim。
- **字段级**：`why/mechanism/projectUsage/caseSummary` 没有各自的证据引用属性；`boundaries[]` 与 `interviewLens[]` 有 `sourceFragmentIds`。
- **可点击性**：网页无来源点击或详情；当前最多能在代码/测试里追溯 fragment → sourceId/location/text，并做引用存在性与来源层校验。
- **来源类别**：`course/project/industry/inference/jd/interview` 已在类型中允许，但题目中的 `course_fact/project_fact/inference/jd_signal/interview_signal` 并非当前实际枚举。H02 当前只接课程与项目片段，Canonical/JD/Interview 的真实材料尚未作为对应 H02 片段录入。

## 9. Interview Lens 的实际挂载

有两种**独立数据结构**：Card 内 `interviewLens[]`（`question + answerFocus + sourceFragmentIds`）和全局 `interviewQuestions[]`（`id + nodeId + question + answerOutline[]`），均可通过 Node 关联，均允许多个问题。H02 当前两处各有一个相关但不完全同文的问题。网页没有 Lens renderer，也没有隐藏、展开、Overlay、Drawer 或跨页面复用。需在一次性 renderer 接入时确定主数据入口或映射规则，否则可能重复维护。

## 10. Case 的实际挂载

Node Schema 本身没有 `caseId` 字段；Card 有文本 `caseSummary`，全局 `cases[]` 的 `steps[]` 可顺序引用多个 `nodeId` 和 `viaRelationId`。`case:product-faq-rag` 是经校验的 canonical ID 路径 Seed，**不是 S3 页面**；侧栏 Case 仍禁用。当前 `card:h02-context.caseSummary` 和 `case:product-faq-rag` 分别维护，Card 上没有直接的 `caseId` 引用。因此目前尚未做到“小 Case 与 S3 Trace 从同一 canonical Case 自动派生”。未来可以保持短摘要与结构化 Trace 分工，但需要显式关联/渲染，不能声称已经实现。

## 11. 已验收 H02 的真实最小导入接口

当前**没有** `src/data/nodes/h02.ts` 或可填写后立即出现 Card 的页面接口。实际操作分两阶段：

1. **内容入库**：在 `content/authoringContent.ts:23,84-97` 对齐 `node:h02-context` 与 `card:h02-context`，填完整七点、3 条边界和 5 个 Lens；在 `content/sourceIndex.ts` 加入经核验的课程、项目、JD 等 fragment，并在 Claim/Boundary/Lens/Evidence 中引用真实 ID。不要凭空写来源；现有 `sourceIndex.location` 的本地路径是否仍有效，须在内容验收时单独核实。
2. **一次性网页接入**：为四域到 Node 列表、Node 到 S2 Card 建通用状态/入口；通用 renderer 读取 `src/domain/content/content.ts` 的 `content` 和 `sources`，显示 Card、Lens、Evidence、Relation/Case 关联；不改已冻结 S0/S0-L 视觉，也不为 H02 单独硬编码页面。
3. **验证**：运行 `npm test`、`npm run typecheck`、`npm run build`；浏览器从 S0/S0-L 进入 Harness → H02 → S2，逐项核对七点、来源点击、5 个问题、3 条边界与返回路径。**目前这条浏览器验收链路尚不存在**，不能给出一个真实可打开的 `/h02` 路由。

本次审计对现有工程只做了运行验证：61/61 tests、typecheck、build 均通过；这证明当前数据/工程能编译，不证明尚未实现的 S2 内容展示已通过。

## 12. 六个最终结论

1. **能否正式开始导入已验收 Card？** 可以整理并校验内容数据，**不能按“导入后网页可见”标准正式批量上线**；先需一次性接入通用内容视图。
2. **H02 能否做第一张 Seed Card？** 可以作为第一张接入验证对象；现有 H02 是 `reviewed` 的部分 Seed，需补足题目要求并再次验收，不把当前 reviewed 自动视为用户最终冻结。
3. **真实数据入口在哪里？** `content/authoringContent.ts` 的 `knowledgeCards[]`（并配套 `nodes[]/relations[]/cases[]/interviewQuestions[]/evidence[]`）和 `content/sourceIndex.ts`；Schema 在 `src/domain/content/schema.ts` / `sourceSchema.ts`；校验导出在 `src/domain/content/content.ts`。网页目前未使用这个导出。
4. **七点字段与 UI 映射是什么？** 详见第 2 节：七点在 Card Schema 中均有直接或组合字段，但七点**目前都没有实际网页容器**；Interview Lens、Evidence 也未确定现成 Overlay/Drawer。
5. **批量 Filling 前的真正阻塞项？** 仅一组前端接入阻塞：建立 S1/S2 可到达的通用入口和 renderer，并把 canonical content/source 引入 UI；同时确定两套 Interview 问题数据的单一消费规则和 Evidence 的显示/解析。无需重画 S0/S0-L 或重做 Domain 结构。
6. **给第三窗口的下一步建议：C——当前前端还不具备正式导入条件。** 最小理由：S2 不存在、主页面不消费已有 Card 数据，单纯增加 H02 文本不会产生可验收页面。可立即准备 H02 内容，但应把“正式导入并在系统中验收”排在一次性通用接入之后。
